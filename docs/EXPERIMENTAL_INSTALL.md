# Experimental test install (DEV build only)

Lets the owner try any technically installable RG Nano candidate and report what works. It approves nothing: every candidate stays `UNAPPROVED`, hardware test `none`, and nothing here touches `catalog/`, `approvals.json`, signing, or the production OPK.

## What it is
- **Where:** `RetroHatchDev.opk` only (built with `-DRH_DEV -DRH_EXPERIMENTAL`; the production recipe has neither, no ZIP code, no zlib; `tests/test_prod_wiring.py` checks this). State in `/mnt/FunKey/.retrohatch-dev`, installs into `/mnt/Applications` through the same engine (`rh_install.c`: journal, backup, mount/busy check, refuses to touch a file RetroHatch did not install).
- **Code:** `ui/rh_ops_exp.inc` (download, validate, install, uninstall; ~170 lines), `core/rh_zip.c` (one-member ZIP extraction), a few UI hooks in `ui/rh_ui.c`, the DEV program loads `candidates/rg-nano.json`. Everything else is reused.
- **Records:** app id `x-<candidate id>` in the normal `installed.tsv`. The Installed list shows these rows tagged `UNVERIFIED` and opens the candidate page for Uninstall.

## Flow (never automatic; two separate confirmations)
1. Discover > candidate page. The bar says **Test Install** (or a grey reason why not).
2. Confirm screen: `UNVERIFIED. Not approved.`, host, advertised size, hash status. A candidate without a hash says `Publisher not verified` and the button reads **Download anyway**. B or Cancel does nothing.
3. Download over HTTPS from the candidate's own upstream link (certificate and host name always verified, https redirects only, size cap 64 MB per OPK / 100 MB per ZIP, B cancels). A GitLab file-page link (`/-/blob/`) is turned into the raw file of the same project. A ZIP is opened strictly (one member by base name; see below). The result must start with the squashfs magic `hsqs`. Result: `Downloaded, not installed. UNVERIFIED.`
4. The bar becomes **Install (UNVERIFIED)**. Confirm shows file name and SHA-256 of the downloaded file; Install runs the engine. An existing file with that name is never replaced ("A file with that name already exists").
5. **Uninstall test app** removes only a file the engine recorded and whose hash still matches; saves and settings are never touched.

## Hashes
No candidate in the snapshot has a trusted hash today, so every download is "authenticity unverified" and needs the explicit confirmation. If a snapshot entry later carries `package.sha256` (64 lowercase hex), the download is checked against it (for a ZIP: the ZIP) and the confirm button reads **Download**. The SHA-256 computed locally afterwards proves only that the installed bytes equal what was downloaded.

## ZIP rules (`core/rh_zip.c`)
No ZIP64, multi-part, encryption, or methods other than stored/deflate; at most 4096 entries and a 1 MB central directory; the member is found by base name and must be unique; symlinks, directories and special files refused; declared size <= cap and equal to the inflated size, CRC-32 must match, compression ratio bounded; local header must agree with the central directory; the member's path is never used for output (the caller names the destination, opened O_EXCL); nothing is left behind on failure. Names with `..`, absolute paths, backslashes or control characters are refused when they are the requested member.

## Not installable (shown as a grey reason, A does nothing)
No package link ("Source only"); package is not an OPK (the two SDL Retro cores); firmware/system changes and launcher stubs (GMenu2X, SwitchToADB, SwitchToUSB, USBLink, Handheld Link, Counter-Strike, Half-Life); not HTTPS; link too long; package over the cap; a file name the engine denylist refuses.

## Known limits
- **TLS 1.3 download defect: FIXED and hardware-tested on the UI path (2026-11-09).** Found 2026-11-07: `static.miraheze.org` (the FunKey wiki file host) only accepts TLS 1.3 and the old mbedTLS 2.16 client could not talk to it ("TLS handshake failed" for 28 candidates). `core/rh_net.c` now uses the firmware's OpenSSL 1.1.1i (TLS 1.2 minimum, 1.3 negotiated, certificate and host name checks unchanged and mandatory). Evidence: PokeMini (Miraheze) downloaded through the DEV app's own Test Install, hash equal to the PC copy, installed, launched and exited cleanly; GitHub direct OPK and ZIP downloads (Rubido, Znax, 2048) re-run on the Nano with matching hashes; wrong-CA, wrong-host, expired and http:// cases refused (host tests). Only PokeMini was run through the UI; the other 27 Miraheze candidates were not individually retried. The batch results still label those packages PC-staged: they were fetched before this fix. **Maintenance limit:** OpenSSL 1.1.1i is end-of-life and is linked statically from the firmware sysroot (see `docs/NANO_V1_RELEASE.md`, release work).
- "Installable" means RetroHatch will try. A dead link, a ZIP without the named member, or a changed upstream file fails with a message and keeps nothing. The 7 GitLab-hosted wiki apps (Clock App, Dividead, Heboris, NCrafti, SRB2, STK, Worship Vector) answered 403 to every scripted download and have no other public OPK, so they are hidden from the browser (`hidden` in `candidates/inventory.json`, kept in full for recovery). The browser lists 123 candidates, 95 of them with Test Install.
- Installing runs no code; launching the app does. Unverified means unverified: the app may not work or may behave badly.
- **A package that is only a launcher stays a stub.** RetroHatch extracts the one OPK from a ZIP and nothing else. If the app needs the rest of the ZIP (NanoCraft needs `ninecraft`, `runtime/`, `gl/`, `mesa/`, `egl-wrap/`, `lib/` in `/mnt/FunKey/nanocraft/`, plus your own Minecraft APK), it installs but opens and closes. Counter-Strike and Half-Life are greyed out for this reason; other candidates are not checked for it until someone tries them (`more_packages` in the snapshot only counts extra OPKs).
- ZIP members are chosen by the file name the snapshot recorded; a ZIP that holds several OPKs yields only that one.
- The cache keeps downloaded OPKs (`.retrohatch-dev/cache/x-<id>.opk`) so Install can follow Download; delete them by hand if space matters.
- DEV and production keep separate state directories (`.retrohatch-dev` / `.retrohatch`), and the production program contains none of this code, so experimental records can only exist in the DEV state. Keep catalog ids that start with `x-` out of any future signed catalog to avoid a clash in DEV.

## Tests
`python3 tests/test_zip.py` (52 cases, WSL), `python3 tests/test_experimental.py` (479 checks, WSL, local TLS server): classification of the real 130-candidate snapshot, hash good/bad, ZIP good and hostile members, HTML instead of a package, 404, GitLab link, cancel then retry, offline, install/uninstall, clash with an existing file, tampered installed file, unrelated files and saves untouched, the UI screens, and production ops exposing none of it. Plus the unchanged offline suites.

## Batch compatibility test (`tools/batch_test.py`)
One tool that runs every eligible candidate through the experimental installer and the normal FunKey launch path on the real Nano and records what happened (`docs/APP_COMPATIBILITY_RESULTS.md`). It reuses, it does not re-implement:
- **Download, install, uninstall:** the same experimental installer code, driven headless by `platforms/nano/cli/rh_exp_cli.c`. The host build downloads (HTTPS, ZIP member extraction, squashfs check) and the Nano build (`build/rh_exp_arm`, copied to `/tmp`, i.e. RAM) installs through the engine, so every install check applies (hash, denylist, never overwrite what RetroHatch did not install, mount check, journal). Records are `x-<id>` in `installed.tsv`.
- **Inspection before anything runs:** `tools/opk_inspect.py` unpacks the OPK on the PC (never mounts or executes it) and skips unsafe, suspicious or incompatible packages (system-changing commands in launch scripts, device nodes, setuid files, links to system paths, no FunKey desktop entry, Exec target missing, wrong CPU/loader/libraries, unsupported squashfs compression, key maps that run console commands). Packages it cannot judge become NEEDS MANUAL CHECK and are not launched.
- **Launch:** `tools/batch_launch.sh` repeats what the frontend does (`keymap rom`, `opkrun` with `pid record`, then `termfix_all` and `keymap default`), after the launcher is held off with the system's own `/mnt/disable_frontend` switch (a dead-man timer on the Nano removes it if the tool dies). It samples the process, CPU and the framebuffer during a 8 s startup window and 14 s run, then stops the app with SIGTERM (SIGKILL only if it ignores TERM for 8 s, which is a HANG). It never presses a button.
- **Verdicts:** PASS needs a running process, a real picture on screen (at least 16 colours, not uniform), a clean stop and no crash evidence; a process alone is never PASS, and PASS never claims gameplay works. FAIL (exits by itself), CRASH (signal or crash evidence), HANG (ignores TERM), SKIPPED, NEEDS MANUAL CHECK.
- **Safety stops:** the whole run stops on an unexpected reboot (boot id), battery under 25 %, `/mnt` no longer read-write, new kernel storage errors, an app or `/opk` left behind, changed unrelated apps or production state, a key map not back to default, two HANGs in a row, or lost SSH. It never power-cycles, never uninstalls, never touches firmware. Batches of 10 with a full health check between them.
- **Order:** `dry-run` (host only) -> `validate` (first a dead-man self-test: the launcher is held off with a 25 s timer and must come back by itself; then Znax, Rubido, 2048 must PASS, otherwise the batches refuse to run) -> `run`.
Tests: `python3 tests/test_batch.py` (WSL): inspection on hostile and good trees, the verdict rules, and the launch script against stub launchers.
